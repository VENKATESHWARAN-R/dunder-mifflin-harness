dunder-mifflin-harness

A research harness for autonomous software development — built to test whether tiered model routing can match Anthropic's harness quality at 3–5× lower cost.

Give the harness a single prompt. It plans, decomposes the work into tasks, routes each task to the right model tier (Haiku for trivial CRUD, Sonnet for logic, Opus for architecture), builds, evaluates, and iterates — all autonomously, with full cost tracking and an audit trail of which model handled which task.

1 · The Hypothesis

Anthropic's harness builds working applications autonomously — a Browser DAW in ~4 hours for $124 using Opus 4.6 throughout. Impressive, but expensive. What if most of those tokens could run on cheaper models?

A multi-agent harness with intelligent model routing and structured context engineering can achieve comparable quality at 3–5× lower cost, by routing the majority of token spend through cheaper models while reserving expensive models for high-leverage tasks.

This is a research project, not just a coding agent. Every escalation, every tier assignment, every eval score becomes data — building a body of evidence about which task types genuinely need expensive models and which don't.

2 · What It Looks Like

The user gives the harness a prompt. The harness does the rest.

$ harness "Build a Python CLI note-taking app with markdown storage, tags, and search"

▸ planning (architect / opus-4.7)
decomposed into 9 tasks · cost so far: $0.42

▸ task 1/9 project setup (architect)
⚙ write pyproject.toml +18 lines
⚙ write notes/cli.py +34 lines
✓ passed eval: 1.0 · $0.31

▸ task 2/9 add command (scout / haiku-4.5)
⚙ edit notes/cli.py +22 lines
✓ passed eval: 1.0 · $0.04

▸ task 7/9 search (worker / sonnet-4.6)
⚙ edit notes/cli.py +47 lines
✗ eval failed (0.6) — case-insensitive search broken
↻ retry attempt 2
✓ passed eval: 1.0 · $0.18

▸ run complete 9/9 features · $11.40 · 47 min
The principle: the user sees what's happening (which model, which tool, what cost) but doesn't have to micromanage it. The harness is observable, not chatty.

The system is organised in concentric rings of stability. Inner rings rarely change. Outer rings grow as new capabilities are added. The CLI never knows what's happening in the inner rings.

Why this shape?

Anthropic's harness keeps growing. Ours will too. The question isn't what features to add — it's where do I put a feature so it doesn't break everything else. The answer: put code where its reason to change lives.

Local execution changestools/ (or future execution/)

Each node is uniform: receives state (run_id, task_id, context, config), returns updated state plus status. This is what makes nodes reusable across future workflows.

5 · Tiered Model Routing

Three tiers, provider-agnostic. The plan node assigns each task a tier based on complexity. The hr_escalation node bumps the tier deterministically when a task fails repeatedly — no LLM call needed for the escalation decision itself.

TierModel (default)Use cases
SCOUT anthropic:claude-haiku-4-5 File reading, boilerplate, simple CRUD, formatting, status checks
WORKER anthropic:claude-sonnet-4-6 Feature implementation, testing, evaluation, bug fixes
ARCHITECT anthropic:claude-opus-4-7 Planning, architecture decisions, complex debugging, high-stakes evaluation

The HR escalation pattern

When a task fails N times at its current tier, the escalation node bumps it to the next tier and retries. This is deterministic — just counter checks, not another LLM call. Every escalation is logged, building a research dataset over time about which task types genuinely need which tier.

6 · Persistent State

Everything important lives in SQLite. One file, crash-safe, supports harness resume <run-id>. The schema is the source of truth — see docs/STATE_SCHEMA.md for the contract.

Run-level

runs · tasks · attempts · messages

Every run, every task, every attempt with model/tokens/cost/eval score. The audit trail.

Configuration

agent_configs · context_store

Per-role configs (model, prompt, tools). Scoped context per agent role.

Capabilities

mcp_servers · skills · run_mcp_servers · run_skills

Global registries + per-run enablement junctions. Toggle MCP servers and skills per run or per agent role.

Coordination (v1+)

agent_instances · agent_teams · agent_messages

Future: parallel agents (builder + tester) coordinating via a shared message queue.

7 · MCP & Skills

Tools are MCP-first. Local tools (filesystem, shell, git) exist as Python functions, but anything beyond that is exposed via MCP — Playwright for browser evaluation, Chrome DevTools for inspection, etc. 

# agent_configs.allowed_tools (JSON array)
[
  "filesystem",         # local Tool(fn)
  "shell",              # local Tool(fn)
  "git",                # local Tool(fn)
  "mcp:playwright",     # MCPServerStdio looked up in mcp_servers table
  "mcp:chrome-devtools" # MCPServerStreamableHTTP
]

Per-run enablement means the user can have 20 MCP servers installed but only enable 3 for a specific run — keeping the agent's tool context manageable. Skills work the same way — a frontend skill bundle injects React/CSS conventions into the system prompt only when the task domain calls for it.

8 · Event Contract

The runtime and any UI surface (CLI, browser, A2A) communicate through typed events. The runtime emits, the UI subscribes. Two-way handshakes (approvals, questions) use explicit request/response primitives — never a generic yes/no prompt.

DirectionTypeExamples
Runtime → UI Events (one-way) RunStarted, TaskCompleted, ModelCallCompleted, CostUpdated
Runtime ↔ UI Requests (two-way) ApprovalRequest (file write OK?), QuestionRequest (HITL clarification)
UI → Runtime Commands run(prompt), set_model(...), resolve_approval(...)
Same contract serves the terminal CLI today and a browser UI or A2A server tomorrow. No UI-specific types leak into the runtime.

9 · The V0 Benchmark

V0 success is measured against a single fixed test case: building a Python note-taking CLI from a single prompt. CLI-testable (no browser needed), 7 features, 8–9 expected tasks, multiple tier levels exercised.

The prompt:

Build a Python command-line note-taking app called notes. Create notes with title and body, list, view, search by keyword, add tags, filter by tag, delete. Each note is a markdown file with YAML frontmatter in a notes/ directory.

11 · Beyond V0

V0 proves the harness can autonomously build a CLI app. V1 and beyond expand what it can build and how it operates.

V1 · The escalation harness

  • Dynamic model escalation (HR agent) deterministic counter-based
  • HITL mode as a separate workflow composition
  • Browser evaluation via Playwright MCP
  • Mid-run MCP/skill toggle slash commands
  • Multi-task runs with full task router

V2 · Multi-strategy harness

  • Additional workflows: POC-then-swarm, TDD, agile
  • Strategy selector chooses workflow per prompt
  • Sub-workflow nesting (TDD inside feature-by-feature)
  • Dynamic skills attachment by task domain

V3 · Multi-agent teams

  • Parallel agents (builder + tester) per run
  • Shared message queue (agent_messages)
  • Bug reports flow tester → builder asynchronously
  • Team coordination strategies

V4 · Beyond local

  • Sandboxed execution (Docker, then cloud)
  • A2A server: harness as a callable agent
  • Browser UI subscribing to the same events
  • Cross-domain: infra, migration, refactoring
